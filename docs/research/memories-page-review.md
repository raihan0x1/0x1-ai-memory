### Latensi dan payload

Request GET ke daemon berjalan lewat loopback pada instalasi dengan `local_onnx` 384 dimensi berstatus siap. Tiap alur diukur dengan 15 request berurutan setelah satu warm-up. Waktu mencakup request sampai seluruh body diterima. Maksimum sampel setara dengan p95 metode nearest-rank pada n=15.

| Alur | Median | Maksimum sampel | Body |
| --- | ---: | ---: | ---: |
| Browse, 20 dari 194 | 2,59 ms | 4,16 ms | 16,9 kB |
| Browse, halaman 2 | 2,66 ms | 3,54 ms | 17,3 kB |
| Search `changeset` | 5,29 ms | 11,72 ms | 16,7 kB |
| Search `changeset`, satu proyek | 4,00 ms | 4,66 ms | 3,7 kB |
| Graph, 194 node dan 471 edge | 11,67 ms | 12,31 ms | 218,2 kB |
| Inspector, satu memori | 3,06 ms | 4,42 ms | 9,8 kB |
| Briefing, satu proyek | 0,65 ms | 1,23 ms | 4,0 kB |

Satu percobaan paralel berisi browse, search, dan graph selesai dalam 18,05 ms. Pengukuran ini mencakup basis saat ini dan belum mewakili beban berkelanjutan, ukuran arsip yang lebih besar, atau perpindahan mode embedding. Satu navigasi browser mencatat first contentful paint 72 ms, sebelum hasil list masuk. JavaScript awal berukuran 394,6 kB dan CSS 40,5 kB. Keduanya dilayani tanpa kompresi pada probe dengan `Accept-Encoding: gzip, br` dan punya cache immutable. Satu percobaan membuka Graph mencatat resource 32,4 ms dan dua main-thread long task sebesar 64 dan 75 ms dalam satu detik setelah aksi. Trace atribusi belum diambil. Tick D3 sinkron merupakan kandidat profiling. [Asset handler](../../src/server.rs#L834-L855) · [Layout D3](../../ui/src/components/MemoryGraphCanvas.tsx#L350-L381)

### Akurasi di data lokal

Probe membandingkan ID hasil API dengan kueri FTS5 read-only yang memakai ekspresi prefix dan status yang sama, serta menerapkan filter proyek sebelum memilih kandidat. Untuk `project memory api test data code`, 41 memori cocok secara leksikal di salah satu proyek. Dari 27 hasil API dengan `limit=250`, 26 termasuk dalam himpunan itu. Jadi 15 kecocokan leksikal tidak tampil meski halaman dapat menampung semuanya. Pencarian hybrid juga menemukan tiga hasil untuk `zzzzqvxx01970199197` pada **All projects**, dengan nol kecocokan FTS untuk token itu. Gunakan contoh seperti ini untuk menilai toleransi semantik dan membedakan kecocokan literal dari saran konsep. ## 1. Keandalan hasil pencarian

**P1 · Terapkan filter sebelum mengambil kandidat.** FTS mengambil sampai 60 hasil terbaik dari seluruh arsip. Jalur `vec0` mengambil 60 tetangga global dan menahan yang berjarak kurang dari `0.85`; fallback `LIKE` mengambil sampai 40 baris hanya ketika kedua jalur awal tidak menghasilkan skor. Filter proyek, status, klien, tipe, tag, file, dan `Never recalled` baru dilaksanakan setelah tahap tersebut. Bahkan dengan filter ketat dan kandidat akhirnya kosong, fallback tidak dijalankan ketika peta skor sempat terisi oleh kandidat di luar filter. `total` untuk query teks adalah jumlah kandidat yang lolos, maksimal 120 untuk hybrid, 60 untuk FTS biasa, atau 40 pada fallback. Label jumlah hasil saat ini memberi kesan jumlah seluruh kecocokan. [Retrieval dan fallback](../../src/db.rs#L1034-L1135) · [Predikat](../../src/db.rs#L1923-L1973) · [Label total](../../ui/src/pages/MemoriesPage.tsx#L516-L521)

Mulai dengan FTS dan fallback di dalam himpunan yang memenuhi filter. Pertahankan perilaku `Project` yang menyertakan memori global dan jelaskan itu di UI, karena juga dipakai oleh jalur recall. Verifikasi cara memasukkan himpunan ID atau metadata ke `vec0` versi `0.1.9` yang dikunci repo, lalu pilih bentuk yang lulus tes untuk proyek kecil dan arsip besar. Tentukan apakah UI menjanjikan seluruh kecocokan leksikal atau kumpulan hasil hybrid terbatas. Untuk kumpulan terbatas, tampilkan label seperti “Hasil teratas”. Uji lebih dari 60 pengalih di luar filter, arsip aktif bercampur status, serta proyek yang hanya punya kecocokan semantik. [Predikat proyek](../../src/db.rs#L1923-L1936) · [Pemanggil recall MCP](../../src/mcp.rs#L209) dan [hook](../../src/hooks.rs#L141) · [Versi sqlite-vec](../../Cargo.lock#L2201-L2204) · [KNN sqlite-vec](https://alexgarcia.xyz/sqlite-vec/features/knn.html) · [Metadata saat KNN](https://alexgarcia.xyz/sqlite-vec/features/vec0.html#metadata-columns)

**P2 · Pertahankan kecocokan path dan simbol di depan hasil yang longgar.** Pencarian mengubah maksimal 12 token menjadi awalan yang dihubungkan dengan `OR`. Semua kolom FTS memakai bobot BM25 default. Untuk kueri teknis dengan beberapa segmen, satu token umum bisa membuat fallback substring dilewati. Uji nama file, path, simbol, dan frasa yang memang dicari pengguna. Beri kecocokan literal atau frasa bobot yang sesuai, sambil mempertahankan pencarian konsep. Ukur `ORDER BY rank` dan biaya prefix pendek sebelum menambah prefix index. SQLite mendokumentasikan bahwa `rank` setara dengan BM25 default dan dapat lebih cepat ketika memakai `LIMIT`. [Pembentukan query](../../src/db.rs#L2415-L2426) · [SQL FTS dan fallback](../../src/db.rs#L1036-L1085) · [Skema FTS](../../src/db.rs#L122-L131) · [FTS5 rank](https://www.sqlite.org/fts5.html#sorting_by_auxiliary_function_results) · [Prefix indexes](https://www.sqlite.org/fts5.html#prefix_indexes)

**P2 · Jaga indeks semantik setelah teks atau model berubah.** Update teks disimpan sebelum embedding baru tersedia. Jika embedding gagal, yang lama tetap dipakai. Jika dua update overlap, hasil embedding dari revisi lebih lama bisa selesai terakhir dan menimpa hasil terbaru. Sweep hanya mengambil memori aktif atau pinned yang belum mempunyai vektor. Indeks menyimpan dimensi tetap tanpa identitas model. Gunakan revisi teks untuk menolak hasil embedding yang kedaluwarsa dan batasi pemakaian vektor ke model yang kompatibel. Saat vektor perlu diperbarui, FTS tetap menyediakan hasil. Uji update bersamaan, provider gagal, dan perpindahan model dengan data lama. ## 2. Paging dan respons UI

**P1 · Pindahkan filter, paging, dan hitungan browse ke SQL.** Browse melakukan `ORDER BY` pada hasil join, lalu Rust mem-parsing JSON file, tag, dan klien untuk semua baris. Iterasi berlanjut sampai akhir walaupun halaman pertama sudah penuh. Seluruh operasi memakai satu mutex koneksi SQLite. Mulai dengan `WHERE`, `LIMIT/OFFSET` dan `COUNT(*)` yang memakai predikat sama. Pertahankan kepekaan huruf dan perilaku substring saat memindahkan filter tag/file. Tambahkan `id` sebagai pemecah seri pada browse, graph, dan ranking supaya urutan konsisten saat nilai waktu dan skor sama. Pertahankan kontrol lompat halaman. Evaluasi keyset pagination jika lompat jauh menjadi lambat dan navigasi berurutan sudah cukup untuk kebutuhan pengguna. Ukur rencana kueri sebelum menambah indeks. Inspector sudah mengabaikan respons ketika ID berubah. Terapkan perlindungan serupa untuk semua pemanggil list dan graph, termasuk retry dan refresh setelah update. ## 3. Graph Map dan Inspector

**P1 · Pilih graf dari proyek yang diminta dan tunjukkan cakupan aktif.** `GET /api/graph` membatasi node hasil ke 250, dengan permintaan UI 200. Sebelum filter, loader hanya mempertimbangkan 500 baris global yang pinned atau terbaru. Loader yang sama dipakai Inspector untuk mencari tetangga. Pindahkan filter sebelum `LIMIT` dan tampilkan keterangan sampel jika hasil memang dibatasi. Jika query teks tetap khusus list, pertahankan sebagai draf ketika kembali ke list dan jelaskan filter yang sedang diterapkan pada Graph. Tentukan apakah file dengan path relatif sama di dua proyek boleh terhubung. Algoritme saat ini mengelompokkan `same_file` dari string path yang dinormalisasi. ## Urutan pengerjaan

1. Perbaiki kandidat terfilter pada FTS dan Graph serta cakupan total pencarian. Tambahkan fixture regresi dengan proyek kecil dan lebih dari 500 memori pengalih.
2. Amankan urutan respons, cakupan filter Graph dan invalidasi SSE. Perbaiki chip path, navigasi mode, dan status pencarian pada sesi yang sama.
3. Pindahkan paging browse ke SQL. Ukur p50/p95 untuk browse, kata umum, pencarian berfilter, Graph, dan Inspector pada volume yang ditargetkan dengan satu sesi capture aktif. Bandingkan embedding siap dan fallback FTS.
4. Profilkan layout graf dan pisahkan kode Canvas dari bundle awal jika manfaat terukur. Pertahankan Grouped list, Inspector, dan Briefing Preview sebagai alur yang dapat dibuka dari tempat yang sama.

Audit ini mencakup jalur baca. Pengujian simpan, pin, hapus, screen reader, perangkat sentuh fisik, kegagalan provider, serta beban berkelanjutan belum dilakukan. Detector Impeccable pada TSX dan CSS hanya menjalankan aturan regex. Temuan layout dan keyboard berasal dari browser yang dirender.
